# Орбита — личный календарь и планы

ТЗ для GPT-6.2 Sol. Новый проект для практики 08. После двух рабочих сессий должна получиться версия, которую можно показать на защите. Третья сессия — резерв на визуальную доводку и учебное расписание. Продолжительность сессий ориентировочная. Этот документ фиксирует проектные решения до реализации.

## Задача продукта

У студента есть обязательства с датой и вещи, которыми хочется заняться в будущем. «Орбита» даёт два входа в один процесс. Из плана можно поставить шаг в календарь. Из свободного дня можно выбрать шаг, на который наконец появилось время. При этом дедлайн лабораторной, день рождения друга и поездку можно добавить напрямую.

**Сценарий для защиты.** Открыть план «Снять первый короткий ролик», где уже сохранена ссылка на урок. Перейти в календарь, выбрать свободную субботу, нажать «Выбрать шаг из планов» и назначить «Собрать черновик». Увидеть шаг в субботе, обновить страницу, отметить его выполненным в повестке. Открыть план по ссылке в записи и увидеть изменившийся прогресс. Затем показать поездку, которая одной записью занимает несколько дней и открывается с каждого из них.

## Два основных экрана

### Календарь · главная

- В верхней панели — название «Орбита», переходы «Календарь» и «Планы». Основное действие — «Добавить запись». Стартовая дата — сегодня по локальным часам пользователя.
- В заголовке разворота крупно вывести месяц, рядом — год, стрелки по месяцам и кнопку «Сегодня». Под ним — короткая сводка по отображаемому месяцу, например «3 дедлайна · 2 события · 4 шага». Числа вычислять из данных с учётом фильтров. Дни рождения тоже учитывать, нулевые категории можно опускать.
- На широком экране около 70% ширины занимает месяц, оставшееся — повестка выбранного дня. Неделя начинается с понедельника. У сегодняшнего числа тонкое кольцо, у выбранного — сплошной тёмно-зелёный круг. При переходе стрелкой на другой месяц выбирать первое число, а при возврате кнопкой «Сегодня» — сегодняшний день.
- Два независимых фильтра с возможностью сброса: **сфера** («Учёба», «Личное») и **тип** («Дедлайн», «Событие», «День рождения», «Шаг плана»). Работают на месяц, сводку и повестку одновременно. В пустом месяце показать «Добавить запись», при пустой выдаче фильтра — «Сбросить фильтры».
- В повестке сначала идут записи на весь день, затем записи на время. Для дедлайна — «Сдать до 18:00», для события — время или диапазон дат, для шага — название родительского плана и действие «Отметить выполненным». В пустом дне доступны «Добавить запись» и «Выбрать шаг из планов». Выбор шага доступен и в занятом дне. Если свободных шагов нет, дать переход к планам.
- На телефоне — компактный месяц, под ним повестка. Числа остаются читаемыми, загрузку дня обозначают короткие маркеры, многодневный интервал — тонкая непрерывная полоса в пределах недели. Полные названия и действия доступны ниже. Выбор дня занимает одно касание. Широкая таблица с горизонтальной прокруткой здесь не нужна.

### Планы

- Галерея карточек в две-три колонки, на телефоне — в одну. У карточки цветная графическая обложка, название, счётчик «2 из 5» и текст ближайшего незавершённого шага в порядке списка. Для нового плана без шагов — «Добавить первый шаг».
- Внутри плана — название, заметка, шаги по порядку, материалы. Создание и редактирование плана, добавление шага, назначение, перенос и снятие даты, отметка выполнения. Порядок задаётся последовательностью добавления. Для материала достаточно названия и ссылки `http(s)`. Удаление материала и редактирование опечатки в названии шага доступны внутри плана.
- Шаг без даты виден только в плане. Назначение даты добавляет его в календарь. Перенос перемещает запись, снятие даты убирает её из календаря. Выполнение обновляет прогресс. Запланированный выполненный шаг остаётся в календаре с галочкой. Название и статус в обоих экранах читаются из одного объекта.

## Как именно работают даты

| Тип | Поля в форме | Как выглядит в календаре |
|---|---|---|
| Дедлайн | Название, сфера, дата сдачи, необязательное время | Одна дата, значок флажка, время при наличии |
| Событие | Название, сфера, даты начала и окончания включительно, переключатель «Весь день». Для события на время — время начала и конца | Однодневная запись или цельная полоса в пределах недели. Пересечения допустимы |
| День рождения | Имя, день и месяц. По умолчанию сфера «Личное» | Ежегодная дата со значком подарка. Для 29 февраля в первой версии — только високосные годы |
| Шаг плана | Родительский план, название, необязательная дата, выполненность. Сфера наследуется из плана | Одна дата, ссылка на план и отметка выполнения |

**Пример многодневного события.** «Поездка в Карелию», пятница 27 ноября — среда 2 декабря 2026 года. В ноябрьском развороте полоса тянется с пятницы по воскресенье. На следующей строке продолжается с понедельника по среду, если видны соседние даты декабря. В декабрьском развороте видна та же поездка. В повестке 1 декабря подпись «27 ноя — 2 дек · день 5 из 6». Из любого сегмента открывается одна карточка. Правка диапазона меняет всю поездку. В сводку каждого пересечённого месяца она входит как одно событие.

**Правила для формы и реализации**

1. При открытии с конкретного дня обе даты равны выбранной. Пока окончание отдельно не меняли, оно следует за началом. После ручного изменения окончания сохранять введённое значение и показывать ошибку, если диапазон оказался обратным.
2. Для события на весь день хранить локальные календарные даты в формате `YYYY-MM-DD`. Для события со временем хранить также `HH:mm`. Первая версия — личное расписание в одном локальном времени. Сутки считать по календарным датам, без деления разницы локальных timestamps на 24 часа.
3. Для одного дня и заданного времени конец должен быть позже начала. Ночной поезд с 22:00 пятницы до 07:00 субботы валиден. При окончании ровно в 00:00 следующий день показывать в повестке с пометкой «Окончание в 00:00» согласно правилу включённой конечной даты.
4. Для получения записей на экран использовать пересечение интервалов: `start_date <= visible_end && end_date >= visible_start`. Запрашивать все видимые ячейки, включая дни соседнего месяца. Сводку считать только для именованного месяца.
5. Полосу резать по границам недели и видимого диапазона. На краях у продолжающихся частей — метка продолжения. В каждой неделе сначала располагать многодневные полосы, сохраняя ряд внутри недели, затем однодневные записи. При переполнении ячейки — «ещё N», открывающее полную повестку дня. Два пересекающихся события должны оставаться доступны.

## Визуальное направление

Образ — бумажный ежемесячник с крупной кириллической типографикой. Самая выразительная часть календаря — композиция чисел, свободного пространства и длинных полос поездок. На экране планов ту же палитру используют широкие обложки с простой геометрией: дуги маршрута, кадры киноплёнки, сетка листа. Выбрать три законченных мотива; по умолчанию назначать их последовательно. Никаких внешних запросов за обложкой.

| Элемент | Решение |
|---|---|
| Холст / поверхность / линии | Тёплый фон `#F8F6EF`, светлая карточка `#FFFDF8`, тонкая линия `#D9DBD0` |
| Основной / вторичный текст | `#242C28` и `#5C675F` |
| Основная кнопка, выбранный день | Хвойный `#285641`, белый текст. Кольцо клавиатурного фокуса отделено от заливки светлым зазором |
| Дедлайн / событие / день рождения | Терракотовый текст `#7A3D20` на `#F7E2D3`, синий `#324C73` на `#E0E9F5`, сливовый `#483C69` на `#EBE5F4`. Шаги — хвойный на светло-зелёном. У каждого типа свой знак или подпись |
| Шрифты | PT Serif для месяца и заголовков планов, Inter для интерфейса и чисел. Поставлять локально с кириллицей. Месяц 48–56 px на desktop и 32–36 px на телефоне, основной текст 15–16 px |
| Ритм | Отступы 4/8/12/16/24/32/48 px, панели с радиусом 14–16 px, полосы событий 5–6 px. Разделять дни тонкими линиями. Тень оставить для открытого диалога |

**Макет до реализации.** GPT-6.2 Sol создаёт самостоятельный кликабельный HTML/CSS-прототип в `design/prototype.html`, открываемый из файла без установки, со сценарными данными. Это выбранный инструмент AI-прототипирования. Переключатель состояний разместить отдельно от интерфейса продукта. Обязательные виды: месяц с поездкой, выбор шага, заполненная форма, отправка, успех, ошибка с сохранённым вводом, пустой день, экран плана; также мобильный месяц и повестка. При проверке использовать одни даты и названия в макете и реализации. Если дизайн изменился, обновить экспорт и записать причину. Сохранить исходное предложение AI и фактическую правку после просмотра в двух-трёх предложениях.

## Архитектура и граница бэкенда

**Клиент.** React + TypeScript + Vite, Mantine, CSS Modules. `MantineProvider` хранит токены и типографику. Из Mantine взять Button, ActionIcon, TextInput, NativeSelect/Select, Checkbox, Card, Modal, Alert, Skeleton. Месячная сетка и полосы — небольшие собственные компоненты на CSS Grid. Для расчётов календаря использовать date-fns с русской локалью. Для сервера — обычный `fetch` через типизированный модуль. Выбор дня, фильтры и состояние формы — локальное состояние React. Страницы: `/calendar`, `/plans`, `/plans/:id`. Выбранную дату хранить в query-параметре, чтобы возврат из плана открывал прежний день.

**Сервер.** Один FastAPI-процесс и один локальный файл SQLite через стандартный `sqlite3`. Сервер отвечает за запись, чтение, проверку полей и связи сущностей. Навигация, раскладка полос, сводка и прогресс — клиентские. Vite проксирует `/api` на локальный сервер. В объём двух сессий входят личная локальная работа и демонстрационные данные. Аккаунты, внешние календари, уведомления, drag-and-drop, облачное развёртывание и n8n остаются за границей задачи.

| Данные | Что хранить |
|---|---|
| `entries` | ID, тип обычной записи, название, сфера, даты/время либо месяц и день рождения. Проверять поля по типу |
| `plans` | ID, название, сфера, заметка, мотив обложки |
| `steps` | ID, plan_id, позиция, название, nullable scheduled_date, done |
| `resources` | ID, plan_id, название и URL |

**Контракт API.** `GET /api/calendar?from=…&to=…` возвращает `{items: [...]}`. Элемент содержит `id`, `kind`, `title`, `area`, `startDate`, `endDate`, необязательные времена; у шага также `planId`, `planTitle`, `done`. Для дня рождения в ответе выдаётся вхождение в запрошенный период. Идентичность элемента — тип, ID и, для ежегодной даты, год вхождения. Сервер включает в выборку шаги с назначенной датой напрямую из `steps`.

- Обычные записи — `POST /api/entries`, `PATCH|DELETE /api/entries/:id`. Удаление поездки явно подтверждать как удаление всего события.
- Планы — `GET|POST /api/plans`, `GET|PATCH /api/plans/:id`. Детальный ответ содержит шаги и материалы. Список отдаёт данные для карточек. Для выбора свободного шага использовать `GET /api/steps?unscheduled=true&done=false`.
- Шаги — `POST /api/plans/:id/steps`, `PATCH /api/steps/:id`. Три действия (назвать, назначить, выполнить) работают через эти ручки. Материалы — `POST /api/plans/:id/resources`, `DELETE /api/resources/:id`.
- Ошибки проверки полей возвращают 422 с указанием поля, отсутствующий объект — 404. При ошибке записи форма остаётся открытой с введёнными значениями. Повторная попытка доступна после завершения запроса. Для создания применять уникальный ID операции или записи и сохранять его на повтор того же запроса. В форме блокировать вторую отправку синхронно до первого `await`, показывать ожидание и отключать кнопку.
- После успешной мутации использовать сохранённую сервером сущность или перечитать затронутые данные. Успешную запись с последующей ошибкой обновления списка нельзя предлагать «создать ещё раз». При быстром перелистывании месяцев устаревший ответ не должен заменить текущий.

**Размещение.** Рабочая директория — открытая в приложении папка репозитория `ITMOv2` на Windows; команды выполняются в PowerShell, новая ветка `homework-08` от актуального `origin/main` личного форка. Если ветка уже существует, продолжить её после проверки состояния. При занятой рабочей копии использовать отдельный worktree. Проект разместить в `practices/practice_08/orbita/`, сохранить учебный README практики, свой README положить внутрь проекта.

## Проверки и доказательства для 12-балльной рубрики

Один стек клиентских тестов — Playwright Test с Chromium. Проверять компоненты через наблюдаемые действия в браузере. В тестах состояний применять `page.route` с ответами того же формата, что реальный API. Один отдельный сквозной прогон выполнять без перехвата сети с временной SQLite. Использовать предсказуемую дату и изолированные данные. Настоящую демобазу не очищать тестовой командой.

**Дополнительно для календаря:** один день; поездка через воскресенье и границу месяца; событие, начавшееся до всего видимого диапазона; пересечение двух поездок; правка с промежуточного дня; ежегодный день рождения и 29 февраля; снятие и перенос даты шага; очистка фильтров; отсутствие горизонтальной прокрутки при ширине 360 px. В успешном тесте поездки проверить, что в сводке одно событие при нескольких видимых сегментах. Для суммы тестового раздела README требует прохождения всех клиентских тестов.

**Проверка качества AI-тестов.** Временно скрыть вывод серверной ошибки. Запустить нацеленный тест, убедиться, что он падает по ожидаемой причине, восстановить поведение и повторить полный прогон. Сохранить настоящие результаты, причину красного теста и итог. Для демонстрации загрузки и ошибки делать воспроизводимые снимки с пометкой «тестовая задержка» / «тестовый ответ 500». Основной демонстрационный сценарий снять на реальном API.

## Контракт запуска и сдачи для агента

Реализовать из корня `orbita/` команды ниже и указать проверенные версии Python и Node в README. Объявить эти команды в package.json в корне orbita/. Проверить их в PowerShell на Windows. Это команды приёмки будущего проекта.

```powershell
npm run setup        # окружение Python, зависимости клиента и Chromium
npm run seed         # повторяемое наполнение отдельной локальной демобазы
npm run dev          # фронтенд и API вместе, локальный адрес в README
npm run test-client  # все клиентские тесты, включая сценарий с временной БД
npm run build        # TypeScript и production-сборка
```

Обычный seed привязать к текущему месяцу, чтобы первый экран был наполнен на защите. Для сравнения с прототипом и тестов предусмотреть фиксированный месяц и дату. Использовать учебные примеры без персональных данных. Не перезаписывать пользовательские записи при повторном seed.

**Итог сдачи:** код и тесты в форке, README с запуском и настройками, ссылка на экспорт прототипа, описание сценария, скриншоты обычного вида/мобильного экрана/загрузки/пустых данных/успеха/ошибки, вывод всех клиентских тестов, примеры реальных запросов к AI для макета, интерфейса и тестов с фактическими правками.
